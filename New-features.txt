PHASE 8 — Compliance & Global Suppression Engine

Priority: 🔴 Critical before public automated sending
Status: ⏳ Specification Ready — Pending Implementation

What's Already in Place:
- Mailbox-level quota enforcement: Mailbox.canSend() checks daily limit and health score.
- Inbound unsubscribe detection: replyClassification.service tags lead with "unsubscribed" and halts sequence enrollment.
- Hard bounce handling: sendingEngine marks lead as "bounced" and cancels remaining jobs.

How It Should Be Implemented:

1. Data Architecture — Suppression Model (models/Suppression.model.ts):
   Suppression {
     workspaceId: ObjectId | null,     // null = global system-wide suppression
     type: "email" | "domain",          // target email address or entire company domain
     value: string,                     // lowercase sanitized email or domain (e.g., "competitor.com")
     reason: "unsubscribe" | "hard_bounce" | "manual_dnc" | "complaint" | "spam_report",
     source: "lead_reply" | "admin_upload" | "bounce_webhook" | "api",
     notes?: string,
     expiresAt?: Date,                  // null = permanent, or temporary cooldown date
     createdBy?: ObjectId,
     createdAt: Date
   }
   Indexes:
   - { workspaceId: 1, type: 1, value: 1 } (unique compound index)
   - { value: 1 } (fast global suppression lookup)

2. Central Compliance Gateway (services/compliance.service.ts):
   export async function canSend(params: {
     leadId: string | ObjectId;
     workspaceId: string | ObjectId;
     mailboxId: string | ObjectId;
   }): Promise<{ allowed: boolean; reason?: string }>
   
   Enforces the 7-Point Compliance Checklist before any SendJob leaves the queue:
   ① Is lead.email or lead.company.domain in the workspace or global Suppression list?
   ② Is lead tagged with "unsubscribed" or status === "bounced"?
   ③ Is lead emailVerification.status === "invalid" or "disposable"?
   ④ Has this lead been contacted within the workspace cooldown window (e.g., max 1 touch per 24 hours)?
   ⑤ Is the associated SequenceEnrollment still active (not stopped/completed)?
   ⑥ Is the Mailbox active, healthy (healthScore > 50), and within daily quota?
   ⑦ Does the lead reside in an active Do-Not-Contact (DNC) list?

3. Send Engine Integration (services/sendJob.service.ts):
   Inside processSendJob(), call canSend() immediately prior to transport dispatch:
   const complianceCheck = await canSend({ leadId: job.leadId, workspaceId: job.workspaceId, mailboxId: job.mailboxId });
   if (!complianceCheck.allowed) {
     job.status = "cancelled";
     job.lastError = `Compliance check failed: ${complianceCheck.reason}`;
     await job.save();
     return { success: false, status: "cancelled", error: job.lastError };
   }

4. Unsubscribe Headers & 1-Click Opt-Out (RFC 8058):
   - Inject List-Unsubscribe: <https://api.coldmailer.ai/v1/compliance/unsubscribe?token=...>, <mailto:unsub@domain.com?subject=unsubscribe>
   - Inject List-Unsubscribe-Post: List-Unsubscribe=One-Click into all outbound MIME headers.
   - Public Unsubscribe Controller: GET /api/v1/compliance/unsubscribe verifies HMAC token, inserts into Suppression collection, tags lead, and shows clean confirmation page.

5. REST API Endpoints (routes/compliance.routes.ts):
   - GET    /api/v1/compliance/suppressions        (filter by type, search, pagination)
   - POST   /api/v1/compliance/suppressions        (manually add email/domain to DNC)
   - POST   /api/v1/compliance/suppressions/bulk   (CSV upload of DNC list)

2. Centralized Permission Matrix (constants/permissions.ts):
   export const PERMISSIONS = {
     // Leads
     "lead.read": ["owner", "admin", "manager", "sales_rep", "viewer"],
     "lead.create": ["owner", "admin", "manager", "sales_rep"],
     "lead.update": ["owner", "admin", "manager", "sales_rep"],

     // Mailboxes

     "mailbox.disconnect": ["owner", "admin"],
     "mailbox.send": ["owner", "admin", "manager", "sales_rep"],

     // Analytics
     "analytics.view": ["owner", "admin", "manager", "sales_rep", "viewer"],
     "analytics.export": ["owner", "admin", "manager"],

     // Workspace & Settings
     "workspace.invite": ["owner", "admin"],
     "workspace.remove_member": ["owner", "admin"],
     "workspace.billing": ["owner"]
   } as const;

3. Declarative Authorization Middleware (middlewares/rbac.middleware.ts):
   Never hardcode `if (user.role === "admin")` inside controllers.
   Implement a reusable, declarative middleware:
   ```ts
   export const authorize = (permission: keyof typeof PERMISSIONS) => {
     return (req: Request, _res: Response, next: NextFunction) => {
       const role = req.workspaceRole || "viewer";
       const allowedRoles = PERMISSIONS[permission];

       if (!allowedRoles.includes(role)) {
         throw new ApiError(403, `Forbidden: You do not have permission '${permission}'`);
       }
       next();
     };
   };
   ```

4. Route Protection Integration:

   router.delete("/leads/:id", authMiddleware, workspaceMiddleware, authorize("lead.delete"), deleteLeadController);
   router.post("/mailboxes/connect-smtp", authMiddleware, workspaceMiddleware, authorize("mailbox.connect"), connectMailboxController);

5. Frontend Permission Guard (hooks/usePermissions.ts):
   Hook returning `{ can: (perm) => boolean, role }` to dynamically disable/hide action buttons (e.g., Launch Sequence button disabled for `sales_rep` or `viewer`).

Priority: 🟡 Later — Post-Core Scalability

How It Should Be Implemented:

1. Multi-Provider Abstraction Architecture (services/enrichment.service.ts):

     ```ts
     interface IEnrichmentProvider {
       enrichCompany(domain: string): Promise<CompanyEnrichmentData>;

     }
     ```

2. 4-Stage Enrichment Pipeline:
   Stage 1 — Domain Extraction: Parse domain from lead email or company website.
   Stage 2 — Cache Verification: Check `EnrichmentCache` collection (30-day TTL) to prevent duplicate API credit burn.
   Stage 3 — Provider Dispatch: Query primary provider (e.g. Apollo), falling back to secondary (e.g. Clearbit) on miss.
   Stage 4 — Lead Schema Merging:
     - Company: industry, employee count, estimated revenue, founded year, tech stack, funding round.
     - Person: verified job title, LinkedIn profile URL, phone number, location, timezone.
     - Merges clean attributes into `lead.company` and `lead.customFields`.

3. Cost & Credit Protection:
   - Workspace-level credit quota controls preventing unexpected third-party provider billing overages.
   - Automatic domain deduplication so 10 leads from "acme.com" only consume 1 company enrichment credit.

4. REST API & UI Trigger:
   - POST /api/v1/leads/:id/enrich (Single lead enrichment on demand)
   - POST /api/v1/leads/bulk-enrich (Batch enrichment for selected leads or dynamic saved segment)
   - Lead Detail UI: "Enrich Lead Data" action button with live loading spinner and updated badge indicators.
